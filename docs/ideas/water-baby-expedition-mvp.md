# 水宝宝远行与家园修缮 MVP

## 文档状态

- 状态：首个可用切片已实现；正式角色美术与用户验证待后续完成
- 定位：轻量养成，不是宠物模拟器
- 适用端：桌面端；小程序实现与发布不在本仓库验证范围内
- 核心目标：让喝水、果实库存和长期养成形成闭环，同时严格限制系统规模

## Problem Statement

如何让用户每天合理喝水后产生一次值得期待的轻量反馈，并让现有果实成为有意义的探险资源，而不把 Drink Water 扩展成需要频繁照料、复杂合成和数值经营的独立游戏？

## Recommended Direction

增加一个“水宝宝”角色。水宝宝不具备饥饿、清洁、健康值、情绪惩罚或频繁对话；它只承担三个职责：展示当天可出发状态、携带一种已收获作物外出、归来后带回种子或基础材料。

基础材料仅包含木头和石头。它们不进入开放式合成系统，而是用于完成少量、固定、一次性的家园修缮项目。每个项目永久解锁一个新探险地点或选择，不产生可继续升级的建筑链。

首版不实现工作台、厨具和烹饪。未来只有在“用户愿意持续准备探险”这一核心假设得到验证后，才考虑把灶台作为一个新项目，并让料理改变探险规则，而不是单纯增加数值。

## 体验原则

1. **低频**：每天最多发起一次探险；一次准备、一次领取即可完成闭环。
2. **不制造负罪感**：漏喝水时水宝宝只休息，不生病、不挨饿、不离家出走。
3. **不奖励过量饮水**：只按当天目标完成比例判断出发档位，达到 100% 后不再增加收益。
4. **果实是选择，不是税**：用户主动选择一种果实作为便当；不同等级影响奖励倾向，但不存在唯一最优作物。
5. **回报必须可消费**：首版回报只包含现有种子、木头和石头，不制作纯收藏明信片。
6. **建设必须有限**：项目数量少、成本固定、完成即结束；不做自由摆放、生产队列或无限升级。

## 核心循环

```text
记录饮水
  → 当日目标进度达到出发门槛
  → 选择一个已收获作物作为便当
  → 水宝宝自动外出
  → 到时后领取种子 / 木头 / 石头
  → 用材料完成固定修缮项目
  → 永久解锁新的探险地点和奖励倾向
```

## MVP Scope

本期范围由以下规则、状态和界面共同限定。

### 1. 当日出发资格

不创建可无限积累的“喝水货币”。出发资格从当日饮水快照实时派生，避免超额饮水获得额外奖励。

| 当日进度 | 可选探险 | 建议时长 | 奖励份数 |
| --- | --- | ---: | ---: |
| `0 ml` | 不可出发 | - | - |
| `1 ml - 99%` | 短途 | 4 小时 | 1 份 |
| `>= 100%` | 远途 | 8 小时 | 2 份 |

约束：

- 每个自然日最多发起一次探险，以本地 `dayKey` 为准。
- 达到 100% 后继续记录饮水不会增加时长、奖励份数或稀有率。
- 撤销饮水会实时影响尚未开始的出发资格；已经开始的探险不撤销，避免产生负库存或复杂回滚。
- 补记昨天不补发已经错过的探险次数，防止历史记录一次性生成大量资源。
- 时长和奖励份数均应配置化；表中数值是首轮验证默认值，不是永久经济参数。

### 2. 探险准备

发起探险时只要求两个选择：

1. 从已解锁地点中选择一个目的地。
2. 从 `garden.produce` 中选择并消耗一个果实作为便当。

首版使用现有作物 `tier` 决定奖励倾向：

- Tier 1：更偏向木头，适合早期修缮。
- Tier 2：木头、石头和种子相对均衡。
- Tier 3：更偏向种子和较高等级种子池。

“偏向”只改变权重，不保证具体奖励。所有概率在发起时一次性确定并存入探险状态，领取或重启应用不能重抽。

### 3. 探险状态

同一时间只能有一个进行中的探险。状态只有：

- `atHome`：在家，可查看出发资格。
- `exploring`：外出中，只显示目的地和预计归来时间。
- `readyToClaim`：已经归来，等待用户领取。

领取是必要交互，奖励不在后台静默进入库存。应用启动、切换到今日页或农场页时只需要根据 `returnsAt` 派生 `readyToClaim`，不额外创建后台定时任务。

### 4. 奖励

奖励类型固定为：

```ts
type ExpeditionReward =
  | { kind: "material"; materialType: "wood" | "stone"; count: number }
  | { kind: "seed"; seedType: string; count: number };
```

首版经济约束：

- 种子奖励必须复用现有种子配置和库存字段。
- 单次奖励数量设置硬上限，防止随机或配置错误破坏库存经济。
- 默认地点也必须能产出木头和石头，确保新用户不会因未解锁地点而卡死。
- 不掉落明信片、角色经验、装备、金币或新的稀有度货币。

### 5. 固定修缮项目

首版建议三个项目。名称、成本和解锁内容均配置化，以下为验证用默认值：

| 项目 | 建议成本 | 永久效果 |
| --- | --- | --- |
| 林间木桥 | 木头 8、石头 4 | 解锁森林路线；木头产出更稳定 |
| 山脚石阶 | 木头 4、石头 10 | 解锁山地路线；石头产出更稳定 |
| 河畔渡口 | 木头 10、石头 8 | 解锁河岸路线；种子奖励倾向更高 |

项目规则：

- 材料足够时一次性建造，不支持分批捐献，避免增加项目进度同步状态。
- 每个项目只能完成一次，完成后只保存稳定项目 ID。
- 项目不能升级，不产生材料，不缩短喝水提醒，也不改变健康目标。
- 地点差异以奖励权重和简短文案为主；首版不要求每个地点制作多张事件插画。

## UI 与素材预算

### 今日页

水宝宝不再占用今日页底部卡片，而是复用“今日饮水”右侧的圆形进度泡泡：

- 当天尚未喝水时仍显示普通百分比；喝第一口水后，泡泡中央出现可点击的水宝宝形象。
- 外出中和已归来时始终保留同一入口，并通过状态角标区分探索和待领取。
- 点击水宝宝打开模态弹窗；路线、旅行便当、出发、归来信息和领取奖励全部在弹窗内完成。
- 弹窗支持关闭按钮、点击遮罩关闭、Escape 关闭和键盘焦点约束。
- 不显示饥饿、心情、等级、经验条或连续签到压力。

### 农场页

增加“远行与家园”区域：

- 当前木头和石头数量。
- 已解锁地点。
- 三个修缮项目及材料需求。
- 进行中探险的目的地与归来时间。

### 首版素材上限

- 水宝宝 3 个状态图：在家、外出标记、归来。
- 木头、石头各 1 个图标。
- 3 个项目各 1 个小图标或场景局部图。
- 地点复用现有背景语言，可先使用色块、图标和文字，不制作明信片系列。

如果首版素材需求继续增长，应优先砍事件插画和建筑阶段图，不能通过扩大占位素材债务来维持范围。

## 数据契约建议

水宝宝状态属于农场域，作为 `GardenState` 的可选兼容字段持久化：

```ts
type GardenMaterialInventory = {
  wood: number;
  stone: number;
};

type ActiveExpedition = {
  expeditionId: string;
  dayKey: string;
  routeId: string;
  supplyCropType: string;
  startedAt: string;
  returnsAt: string;
  rewards: ExpeditionReward[];
  claimedAt?: string | null;
};

type WaterBabyState = {
  materials: GardenMaterialInventory;
  completedProjectIds: string[];
  lastExpeditionStartedDay: string | null;
  activeExpedition: ActiveExpedition | null;
};

type GardenState = {
  // 现有字段保持不变
  waterBaby: WaterBabyState;
};
```

兼容要求：

- Rust 字段使用 `#[serde(default)]`，旧 JSON 缺少 `waterBaby` 时生成空材料、空项目和无探险的默认状态。
- TypeScript、Rust、Worker 输入校验和消费方文档必须同步更新。
- `normalize_garden` 合并重复项目 ID、丢弃未知项目/地点 ID，并限制材料和奖励数量上限。
- 奖励在开始时生成并持久化；`claim_expedition` 必须幂等，重复调用不能重复入账。
- 建造操作必须在一次本地锁内同时校验、扣材料和加入项目 ID。

## 命令边界建议

新增的 Tauri 命令保持与现有农场命令相同的“锁内校验和修改 → 保存 JSON → 返回完整 `GardenState`”模式：

```text
start_expedition(routeId, cropType)
claim_expedition(expeditionId)
build_garden_project(projectId)
```

每次成功操作都需要：

- 调用 `touch_garden_snapshot`。
- 保存本地状态。
- 触发现有农场快照后台同步。
- 必要时重新判定相关成就；首版可以不新增探险成就。

## 同步与冲突语义

现有农场使用完整快照 Last-Write-Wins，水宝宝状态随完整 `GardenState` 一起同步，不新增 D1 表。

接受以下边界：

- 两台离线设备同时开始不同探险时，较新的农场快照覆盖较旧快照，不尝试合并。
- 材料库存不做自动相加，项目 ID 不单独做集合并集。
- UI 在有进行中探险时应减少重复操作入口，但不宣称支持多设备并发经营。

之所以不做分批建造、多个探险队列和制作队列，是因为这些状态在 LWW 下更容易被覆盖，且与轻量目标不符。

## Key Assumptions to Validate

- [ ] 用户愿意在达到饮水门槛后，每天主动准备一次探险。验证：首版记录本地匿名计数或小范围测试，观察有资格用户的出发率。
- [ ] 果实的奖励倾向足以让用户感到“选择便当有意义”，但不会迫使用户查询攻略。验证：测试用户能否在不阅读长说明的情况下说出不同 Tier 的大致差别。
- [ ] 固定项目和地点解锁比纯收藏更能驱动重复探险。验证：观察完成第一个项目后是否继续发起探险，以及用户是否能说出下一个想建的目标。
- [ ] 每日一次不会显得过于稀薄。验证：比较 4 小时短途和 8 小时远途后，用户是否仍愿意次日回来领取/出发。
- [ ] 木头与石头不会让现有种子兑换、背景兑换失去存在感。验证：检查首版经济中三类消费目标是否各自清晰，不出现所有果实都只用于探险的唯一最优路径。

## 成功标准

首轮验证重点不是材料产量，而是闭环是否成立：

- 有出发资格的测试用户中，多数能在不解释系统的情况下完成首次探险。
- 完成首次探险的用户中，有明确比例在后续自然日再次出发。
- 用户能理解“喝水决定能否出发、果实决定奖励倾向、材料用于解锁地点”三层关系。
- 用户不会为了获得更多奖励而误以为需要超过每日目标继续饮水。
- 单日必要交互不超过“准备一次、领取一次、偶尔建造一次”。

## MVP 实施切片

1. **状态与规则**：Rust/TypeScript 数据结构、旧 JSON 默认迁移、奖励上限和规则配置。
2. **核心命令**：开始探险、领取奖励、建造项目及 Rust 单元测试。
3. **前端接线**：API、控制器、农场快照后台同步和错误映射。
4. **最小 UI**：今日饮水进度泡泡入口、统一探险弹窗、归来领取、农场页材料与项目列表。
5. **配置与文案**：中英文 i18n、地点/项目/奖励权重配置，失败时使用内置配置。
6. **同步验证**：旧客户端快照、双设备 LWW、重复领取、导入导出和完整云备份。
7. **素材替换**：逻辑可先使用明确的开发占位，正式合入前替换为限定预算内的角色和资源素材。

## Not Doing（本期明确不做）

- **宠物生存状态**：不做饥饿、疾病、清洁、死亡或负面情绪，避免健康行为被惩罚化。
- **无限喝水货币**：不按原始毫升无限发币，不奖励超过目标的饮水。
- **自由建筑与摆放**：不做地图格、碰撞、旋转、移动、拆除或建筑仓库。
- **建筑等级和生产**：不做升级树、定时产出、离线收益和生产队列。
- **工作台与合成配方**：木头、石头只能用于固定项目。
- **厨具与烹饪**：在探险准备行为未经验证前不增加料理系统。
- **纯收藏旅行物**：不做明信片、纪念品图鉴和需要大量独立美术的掉落池。
- **多探险队列**：同一时间只允许一个探险。
- **材料细粒度云合并**：继续沿用现有农场完整快照 LWW。
- **排行榜竞争化**：不比较材料、建筑或探险次数，避免把轻量陪伴变成压力来源。

## Future Gate：何时才考虑烹饪

只有同时满足以下条件，才进入烹饪设计：

1. 用户确实重复使用探险，而不只是完成一次新手体验。
2. 用户对“果实作为便当”的选择表达出更多策略需求。
3. 至少能定义三种料理，并且每种都改变探险选择或规则，而不是只提供更大的数值。
4. 新系统仍可保持每天一次准备，不能要求逐个处理食材、厨具耐久或制作队列。

满足 Gate 后，第一项扩展应是一个固定“灶台”项目和少量双作物配方；仍不自动扩展到工作台、工具链和自由建造。

## Open Questions

- 水宝宝的正式名称和视觉性格是什么？
- 首轮测试采用 4/8 小时，还是更适合桌面使用节奏的 2/6 小时？
- 三个项目是否需要在当前背景中留下永久视觉变化，还是只在项目列表和地点选择中体现？
- 是否需要给“当天达到 100% 但已经发起短途”的用户提供非数值反馈，避免产生“应该等到晚上再出发”的策略压力？
- 远端运行时配置是否在首版就包含探险规则，还是先使用本地配置并在规则稳定后再开放远端更新？
